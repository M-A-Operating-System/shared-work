# Data AI Assistant — Roadmap

This file captures planned enhancements beyond the current release. Items here are not specified — they are named and scoped at a level sufficient for future prioritisation. Each requires a Product Design Document (PDD) and CDAiO approval before build begins.

## Near-term — Policy and standards corpus

**Objective:** Allow Andi to reason against the organisation's codified policies, data standards, and business process documentation as structured DDA records, via the MCP server.

**Status:** Planned. Requires the DDA policy and standards module to expose structured records in the DDA schema. Each policy, standard, or process document becomes a first-class DDA record — bindable via `@`-binding, accessible as an MCP tool result, and included in governance audit trails.

| Item | Description |
|------|-------------|
| Policy records as MCP tool results | Structured policy and standard records returned by the DDA MCP server, identical access pattern to entity and survey records |
| `@`-binding for policy objects | Policy and standard records added as bindable object types in the typeahead ranking |
| Compliance reasoning | Andi can answer compliance and process questions by retrieving the authoritative policy record, not relying on training data |
| Write — create and delete operations | Entity create and delete operations via MCP. Update and status-change are already in scope; create/delete are a separate decision requiring additional governance controls. |

**Pre-requisites:** DDA policy and standards module delivering structured records; MCP tool descriptions for policy/standards objects; CDAiO approval.

## Phase 2 — Context memory

**Objective:** Allow Andi to recall relevant context from past conversations at the start of a new session, without the user having to re-establish it manually.

| Item | Description |
|------|-------------|
| Session summary injection | At session start, optionally inject a compressed summary of the user's recent conversations (last 30 days) as a labelled `[Recent context]` block. Opt-in per session. Transparent — block is visible and dismissible. Generated by Claude Haiku 4 at session start. |
| Context globbing | User-initiated: pull selected context from one or more past conversations into a new session. Requires a conversation selection UI, a context budget allocator, and provenance labelling. |

**Pre-requisites:** Summarisation infrastructure stable (built in v1); pgvector RAG infrastructure in place.

## Phase 2 — Additional guided workflows

**Objective:** Extend the platform-managed guided workflow library based on v1 usage signals.

| Item | Description |
|------|-------------|
| Data lineage trace | Workflow version of the `trace_lineage` MCP prompt — structured multi-step lineage walk from source feed to governed entity, with Mermaid diagram output. Add if v1 signal data shows demand. |
| Concept comparison | Workflow version of the `compare_concepts` MCP prompt — side-by-side comparison of two entities with quality, ownership, and classification delta. Add if v1 signal data shows demand. |
| User-customisable prompt library | Allow users to save, name, and reuse their own prompt templates. Requires per-user prompt storage and a management UI. Platform-managed prompts remain separate. |

## Phase 2 — Operational tooling

| Item | Description |
|------|-------------|
| Signal dashboard | Read-only admin dashboard surfacing improvement signal volume by type, confidence distribution, issue lifecycle status, cache hit rate, and MCP tool error rate trend. Accessible to CDAiO and audit administrators. |
| Conversation export | Export a conversation as PDF or markdown. Requires data classification inheritance rules to be resolved first (exported conversations may contain governance-sensitive data). |
| Participant limit increase | Raise the shared conversation participant cap above 10. Platform-configured — requires load and permission testing at higher participant counts. |

## Phase 2 — Conversation organisation

**Objective:** Allow users to organise long-running governance work across multiple conversations.

| Item | Description |
|------|-------------|
| Conversation folders / projects | Group conversations by governance domain, review cycle, or project (e.g. "Finance Q3", "Regulatory Audit 2026"). Folders are user-created and personal — not shared. Requires history panel redesign. |
| Real-time presence in shared conversations | Typing indicators and active-viewer presence for participants in a shared conversation. Useful for live governance review sessions. Requires WebSocket infrastructure. |
| Extended thinking mode | Expose Opus 4's extended thinking (reasoning budget) as a user-selectable option for complex multi-domain analysis tasks. Displayed as a collapsible `<thinking>` block in the thread. |

## Phase 2 — Data warehouse access

**Objective:** Allow Andi to query the actual business data warehouse that the DDA governs, so users can ask questions about real data values alongside governance metadata.

| Item | Description |
|------|-------------|
| Read-only data warehouse MCP tool | New MCP server (or extension to the DDA MCP server) that provides read-only SQL query access to the business data warehouse, mediated through the DDA security model. |
| Query result rendering | Warehouse query results rendered as data tables and Vega-Lite charts, consistent with existing rendering rules. |
| Governance + data linkage | When Andi discusses an entity (via entityCrud/MCP), it can also pull actual data rows from the warehouse for that entity — connecting governance metadata to real business data in one conversation. |
| Security and access control | Warehouse access is gated by the same DDA permissions as the governance layer. Users can only query data they are authorised to access. |

**Pre-requisites:** Data warehouse accessible via read-only connection; MCP server or tool extension designed; data classification inheritance resolved so Andi knows which data is safe to surface in conversation.

---

## Phase 2 — Multi-provider AI models

**Objective:** Allow administrators to configure alternative AI providers (OpenAI, Gemini) as the model backend for Data AI Assistant.

| Item | Description |
|------|-------------|
| Provider abstraction layer | The Supabase Edge Function already abstracts the AI provider. This item formalises provider configuration and tests non-Claude models against the DDA system prompt and MCP tool call patterns. |
| Model capability parity | Validate that OpenAI and Gemini models correctly invoke MCP tools, respect system prompt constraints, and produce rendering-compatible outputs (Mermaid, Vega-Lite, math). |
| Provider selection UI | Admin-level provider selection. Users may be able to select provider per session (subject to admin policy). |

---

## Phase 3 — Semantic search (RAG)

**Objective:** Replace structured MCP tool-call entity lookup with semantic search over the full DDA entity corpus.

| Item | Description |
|------|-------------|
| pgvector entity RAG | Embed entity descriptions, model documentation, and governance narratives using pgvector. `search_model` stub (currently dormant) becomes a live semantic search tool. |
| Conversation memory RAG | Extend pgvector to embed past conversation content. Andi retrieves semantically relevant past turns when they are pertinent to the current query — without injecting entire conversation summaries. |
| Embedding refresh pipeline | CDC-triggered re-embedding when entity records change in the DDA governance schema. |

---

## Not in roadmap

| Item | Rationale |
|------|-----------|
| Voice or multimodal input | Not aligned with current DDA platform direction |
| Multi-tenant isolation | Inherits single-tenant assumptions from entityCRUD; would require significant DB restructure |
| General-purpose AI assistant mode | Outside product vision — Andi is a specialist governance assistant |
