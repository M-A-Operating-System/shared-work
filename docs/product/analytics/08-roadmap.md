# AI Analytics Platform — Proposed Roadmap

This document describes one proposed sequence of deliverables for the AI Analytics Platform. It is not the only valid sequence and is not a committed delivery plan. Phase boundaries should be revisited as implementation proceeds, customer feedback is gathered, and technical constraints become clearer. Decisions to resequence or regroup phases should be recorded here; they do not require changes to the product specification.

---

| # | Phase | Build | Business Outcome |
|---|-------|-------|-----------------|
| 1 | **Governed Analytical Core** | **New:** Platform Admin API and Admin Console; Semantic Metrics Registry (SMR) with `proposed → approved` state machine, version history, and fuzzy metric search; Financial Services Reference Model — pre-built seed definitions across six analytical domains (`portfolio`, `performance`, `risk`, `regulatory`, `counterparty`, `benchmarks`); MCP Capability Layer on Cloudflare Workers edge with JWT validation and eight analytical capabilities (`analyse_metric`, `compare_portfolios`, `issuer_concentration`, `risk_breakdown`, `performance_attribution`, `regulatory_metric`, `list_metrics`, `drilldown`); Semantic Intent Layer — deterministic JSON schema validation and Logical Query Plan generation, no AI model; Role-Aware Projection Layer — JWT claim extraction, row predicate injection, column masking, `defaultDenyAll` enforcement; Semantic Execution Governance — cost estimation, classification gate, circuit breakers; Federated Query Planner with SQL warehouse adapter (Snowflake, BigQuery, Databricks, Redshift, Trino, PostgreSQL), semantic layer adapter (dbt MetricFlow, Cube.js), and in-process result assembly; Visualisation Ontology — eight chart contracts with SCL display spec generation; Narrative Synthesis Engine — Claude Haiku for standard queries, Sonnet for regulatory and attribution, result-anchored with numeric leakage validation; Analytical Lineage Store — full computation provenance record per query; vite2img rendering service — Vega-Lite → SVG/PNG for static chart output | Any MCP-compatible consumer — AI assistant, application, or autonomous agent — can query a registered metric and receive a governed, reproducible result with a chart specification, a narrative, and an audit-grade lineage record, scoped to exactly the user's entitlements |
| 2 | **Automated Monitoring and Alerts** | **New:** Scheduled Query Service — any valid `analyse_metric` or `compare_portfolios` call registered to a cron schedule, executing under the owner's entitlements at runtime; Alert Threshold Engine — up to ten threshold conditions per scheduled query supporting `gt`, `lt`, `gte`, `lte`, `eq`, `pct_change_gt` operators, with a breach event written to the lineage store on each trigger; Push Delivery Service — webhook, SMTP, and Slack delivery with exponential-backoff retry; Scheduled Query Admin UI section in the Admin Console (schedule management, threshold configuration, delivery endpoint management, execution history) | Risk officers and portfolio managers receive automated push notifications when a metric breaches its defined threshold — no manual query required; every alert payload carries a lineage reference to the underlying computation |
| 3 | **SMR Authoring Assistance** | **New:** Natural Language → Metric Draft Generator — Claude Sonnet generates a schema-valid SMR YAML draft (`id`, `label`, `formula`, `aggregation`, `dimensions`, `data.domain`, `units`, `description`) from prose input; draft enters the existing `proposed` state and cannot be activated without Application Admin approval; SMR Consistency Checker — cosine-similarity duplicate detection (threshold 0.85), naming conflict detection, and dimension and data-domain mismatch flagging run automatically before the draft is surfaced for review; Metric Draft Review UI — side-by-side prose vs. YAML view with inline editing and one-click submission to the approval workflow | Metric owners propose new definitions in plain English without writing YAML; the platform detects duplicates and structural conflicts automatically before a draft enters the approval workflow, preventing registry pollution |
| 4 | **Cross-Session Memory** | **New:** User Preference Store — per-user persisted defaults (default time period, dimensions, chart type overrides, measure groups) applied at intent resolution; Saved Query Registry — named, version-controlled MCP parameter sets flagged `needs_review` when dependent SMR definitions change; Favourite Metrics Index — per-user priority weighting in `list_metrics` results and disambiguation suggestions; My Workspace UI. **Extends:** SMR service — emits definition-change events consumed by the Saved Query Registry to trigger staleness flags on affected saved queries | Returning users find their analytical context pre-applied; saved queries surface SMR changes as explicit staleness warnings before execution rather than producing silently incorrect results across sessions |
| 5 | **Proactive Analytical Intelligence** | **New:** Anomaly Detection Service — statistical baseline monitoring (rolling mean ± N standard deviations, configurable lookback) over scheduled query result series, generating scoped insight events on breach; Trend Signal Detector — identifies consistent directional movement across configurable consecutive periods; Insight Configuration UI in the Admin Console (per-metric sensitivity controls, role-level opt-in/opt-out). **Extends:** Push Delivery Service — adds proactive insight card payload type (insight type, metric, observed vs. baseline, Haiku-generated narrative, lineage reference); Anomaly Detection Service — adds peer comparison signals when Benchmark Data Service or Regulatory Reference Service backends are registered | The platform surfaces anomalies and trend signals without users submitting queries; portfolio managers and risk officers find scoped, lineage-referenced insight cards, each traceable to the scheduled query result that produced the signal |
| 6 | **Collaborative Sessions** | **New:** Session Sharing Service — tenant-scoped multi-participant analytical sessions with 24-hour join tokens, owner-controlled access revocation; Per-Participant Governance Engine — independent entitlement enforcement per session participant, with each result tagged to the submitting participant's `sub` claim and projection scope; Annotation Layer — free-text annotations on any result card, stored in the session record; Session Export Service — governed PDF (via vite2img) and ZIP export with a lineage URL attached to every exported result | Portfolio managers and risk officers co-explore data in a shared governed session — each participant's results are governed by their own entitlements — and export the session as a lineage-referenced PDF pack for investment committee or regulatory review |
| 7 | **Ecosystem Service Integrations** | **Extends:** Admin API — adds `POST /v1/smr/import` for importing pre-built metric definition packages from the Semantic Registry Service (six financial services packages); all imported definitions enter the `proposed → approval` workflow; FQP backend adapter layer — adds Regulatory Reference Service adapter with `regulatory` data affinity routing and automatic backend fallback; adds Benchmark Data Service adapter with per-tenant licensing enforcement (`BENCHMARK_NOT_LICENSED` error before any data is returned for unlicensed indices) | Regulatory metric values are sourced from the authoritative service on every query; benchmark queries resolve against licensed index data without internal data ingestion, licensing management, or refresh pipelines owned by the tenant |
| 8 | **Regulatory Compliance Modes** | **Extends:** Semantic Execution Governance pipeline — adds Compliance Mode as step 5 (after classification gate, before concurrency check), evaluated from the `complianceMode` tenant configuration field; adds MiFID II mode (mandatory business justification prompts on PII-adjacent dimensions, best-execution `date` dimension enforcement, append-only `analytics.mifid2_trace` writes); adds Basel III/IV mode (`entity` dimension enforcement on regulatory capital metrics, `analytics.regulatory_snapshots` writes, RESTRICTED override on stress scenario metrics); adds SEC Regulation BI mode (recommendation-language rejection and regeneration in Narrative Synthesis Engine, `suitability_record_id` parameter enforcement before execution) | Regulated queries automatically write regime-specific compliance audit records and enforce query-time constraints without per-query manual configuration; the governance pipeline is the enforcement point, not application code |
| 9 | **Cross-Backend Drilldown** | **Extends:** FQP — adds Cross-Backend Affinity Resolver to detect `dataAffinity` boundary crossings in drilldown traversals and route child sub-plans to the appropriate backend while preserving the parent result's governance context and projection scope; adds Drilldown Result Merger to join child rows from multiple backends back to parent rows on shared dimension keys into a single SCL display spec; Analytical Lineage Store — records the affinity boundary crossing, both backends' sub-plans, and the dimension key used to join the traversal | Analysts drill from a warehouse-sourced aggregate into graph-backed entity relationships in one continuous navigation; the backend boundary is transparent to the consumer and the full cross-backend traversal is captured in a single lineage record |
| 10 | **Advanced Query Capabilities** | **Extends:** Semantic Intent Layer — adds `rank_by`, `rank_direction`, `rank_limit`, `rank_percentile` parameters; `window_op` (`moving_average`, `rolling_sum`, `period_over_period`), `window_size`, `window_anchor` parameters; `scenario` parameter for comparison against SMR-registered stress and forecast definitions; inline `benchmark` composition object (blend weights resolved at query time, logged in lineage); FQP result assembly layer — ranking computed across the full assembled result set (not per-backend sub-result); window operations computed at assembly (not delegated to backends); scenario delta computation (actual vs. scenario vs. delta in a single result set); SMR service — adds scenario definition registration | Complex analytical queries — ranking, rolling windows, stress scenario comparisons, and composite benchmarks — are expressible as a single governed call; consumers receive a complete, join-ready result set without requiring multi-call composition |
| 11 | **Open API Surface** | **New:** SMR Browser REST API — paginated `GET /v1/smr/metrics`, `/dimensions`, `/hierarchies` endpoints scoped to the querying user's entitled metric visibility; Lineage Query REST API — `GET /v1/lineage/{result_id}`, `POST /v1/lineage/search` (by user, metric, time range, backend, or governance decision), `GET /v1/lineage/{result_id}/sub-plans`; GraphQL API Gateway — typed schema exposing `analyseMetric`, `comparePortfolios`, `listMetrics`, `getMetricDefinition`, `drilldown` as GraphQL queries, routing through the unchanged governance pipeline. **Extends:** MCP Capability Layer and FQP — adds NDJSON result streaming with four ordered progress events (`intent_resolved`, `entitlements_applied`, `plan_compiled`, `executing`) and a terminal frame containing the complete assembled result and lineage URL; FQP — adds latency-aware Adaptive Planning tracking p50/p95 per registered backend with automatic rerouting on degradation; Admin API and Scheduled Query Service — adds Materialised View registration (pre-computed result sets refreshed on cron, matching queries receive an 800-unit governance cost reduction) | Compliance teams query the lineage store directly for regulatory audit; BI and application teams integrate against REST and GraphQL APIs without routing through the MCP interface; high-frequency queries hit pre-computed materialised views; streaming consumers render progressive query status rather than a static spinner |

## Not in roadmap

| Item | Rationale |
|------|-----------|
| **Raw SQL passthrough** | Architecturally prohibited — violates semantic abstraction over physical exposure and the deterministic computation principle. Not planned at any phase. |
| **Physical schema exposure to AI model** | Architecturally prohibited. The Semantic Intent Layer receives SMR metric and dimension names only — no table names, column names, or JOIN paths. Not planned. |
| **Ad hoc LLM-generated SQL** | Architecturally prohibited. All queries are expressed as validated MCP tool call parameters resolved against the SMR. Not planned. |
| **Unauthenticated analytical access** | JWT validation at the MCP Capability Layer edge is non-negotiable. Not planned. |
| **LLM chart type selection outside Visualisation Ontology** | Chart selection is always governed by registered chart contracts. LLM intent signals are inputs to the ontology, not direct rendering instructions. Not planned. |
| **Cross-tenant result federation** | Tenant boundary is a non-configurable isolation guarantee. Not planned. |
| **Metric value generation by AI model** | Every number in a result is computed from a registered definition applied to data from a registered backend. The Narrative Synthesis Engine produces prose descriptions of computed values — not the values themselves. Not planned. |
