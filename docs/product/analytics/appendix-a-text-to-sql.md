# Appendix A. Text-to-SQL: Appropriate Use and Governance Boundary

## Purpose

This appendix explains why direct Text-to-SQL is useful for exploration but is not, by itself, a sustainable execution foundation for regulated analytics. It supports the position stated in the [Executive Overview](./01-overview.md#why-text-to-sql-is-not-the-long-term-foundation) without repeating the full architecture.

The concern is not SQL, natural-language interfaces, or exploratory analysis. It is the delegation of business interpretation and executable-query generation to a probabilistic model without an intervening governed semantic contract.

In this appendix, **direct Text-to-SQL** means a pattern in which a language model receives a question and physical schema context, generates executable SQL, and submits that SQL to a database. Implementations may add database permissions, query validation, cost controls, and human approval. Those controls are valuable, but they do not establish the approved meaning of a business metric or dataset.

## Where Text-to-SQL Adds Value

Text-to-SQL can shorten the path from a question to an exploratory result. It is particularly useful when:

- an analyst is investigating unfamiliar data;
- the question is ad hoc and low consequence;
- the result is clearly labeled as exploratory;
- the user is qualified to inspect the generated query and its output; and
- the output does not flow directly into a regulated report, automated decision, or reusable business metric.

These interactions can reveal recurring questions, missing metrics, and useful dataset requirements. They are therefore an input to governance: frequently used exploratory logic can be reviewed, tested, and promoted into an approved metric or dataset contract.

## Why It Is Not the Governed Execution Layer

The distinction is not whether both approaches eventually execute SQL. The distinction is where business meaning, authorization, and evidence are established.

| Concern | Direct Text-to-SQL | Governed Semantic Execution |
|---|---|---|
| Business meaning | Inferred from the question, prompt, and schema context for each request. | Resolved to an approved, versioned metric, operation, or dataset contract. |
| Executable query | Generated by the language model. | Produced deterministically from a validated logical plan and approved mappings. |
| Access | Primarily constrained by database permissions and implementation-specific filters. | Expressed as a request-specific projection covering concepts, fields, rows, masks, and classification. |
| Unsupported concepts | May still produce plausible SQL. | Rejected or returned for clarification when no approved definition applies. |
| Change control | Prompt, schema context, model behavior, and query output can change independently. | Definitions, policies, mappings, controls, and software are pinned and versioned. |
| Repeatability | Re-running the same wording can generate a different query. | Re-running against preserved inputs and source state can be compared using recorded versions and digests. |
| Evidence | Often limited to the prompt, generated SQL, database logs, and result. | Correlates interpretation, definitions, entitlements, controls, plans, execution, result, and terminal status. |

### Accuracy

A syntactically valid query is not necessarily a correct business calculation. Physical schemas do not fully express approved formulas, fiscal calendars, null treatment, weighting rules, benchmark selection, or the definition version that applies to a reporting period. Prompt instructions can describe those rules, but they remain guidance to a probabilistic generator rather than an enforced analytical contract.

This difference matters most for calculations that are reused or consequential. A governed path can reject an unknown or incompatible concept. A direct Text-to-SQL path is optimized to produce a query, which can turn ambiguity into a plausible but unsupported answer.

### Traceability

Generated SQL shows what a database was asked to execute. It does not necessarily show why that query represents the approved business definition, which entitlement decision applied, which definition owner approved it, or whether all required controls completed. Database and model logs can contribute evidence, but they do not replace those missing decisions.

### Repeatability

Repeatability requires more than retaining SQL. It requires the request, definition versions, policies, mappings, execution settings, software version, and relevant source state. Direct Text-to-SQL also introduces a probabilistic generation step: the same question can produce a different query after a context, prompt, or model change. Governed semantic execution records the resolved contract and uses deterministic software after interpretation.

### Security and Operational Control

Read-only credentials, parameter binding, statement allowlists, syntax-tree inspection, query budgets, timeouts, row-level security, and approval gates reduce the risk of generated SQL. They should be used where Text-to-SQL is permitted. They address unsafe execution; they do not create approved analytical meaning.

The direct pattern can also expose more physical metadata to the model and user experience than a semantic interface requires. Complex generated queries can create unpredictable cost or load. These are manageable engineering risks for a bounded exploration service, but they strengthen the case for a separate governed execution path for recurring or consequential workloads.

## A Complementary Operating Model

Text-to-SQL and governed semantic execution can coexist behind the same consumer experience if their status and boundaries remain explicit.

1. A user submits an analytical question.
2. The consumer first searches the approved operation and dataset catalog.
3. If an approved contract applies, the request follows the governed execution path.
4. If no approved contract applies and policy permits exploration, the user may choose a separately labeled Text-to-SQL path.
5. Repeated or consequential exploratory logic becomes a candidate for definition, testing, ownership, approval, and registration.

The exploratory output must not silently acquire governed status. Promotion occurs only after the organization has defined the business meaning, validated the result, assigned an owner, established entitlements, and approved the applicable mappings and controls.

| Use Case | Appropriate Path |
|---|---|
| Investigating an unfamiliar dataset | Controlled Text-to-SQL exploration |
| Testing a hypothesis that will be independently reviewed | Controlled Text-to-SQL exploration |
| Prototyping a new metric definition | Exploration followed by formal promotion |
| Producing a recurring management metric | Governed semantic execution |
| Supplying data to an automated or data-mining workflow | Governed dataset contract |
| Supporting a regulated report or consequential decision | Governed semantic execution with the required evidence controls |

## Evaluation Implication

The architectural proposition should be tested rather than accepted from diagrams alone. The [evaluation plan in Section 3.5](./03-technical-implementation.md#35-evaluation-plan-and-decision-gates) compares the governed approach with the organization's current process and a controlled Text-to-SQL implementation using the same questions, source state, permissions, and reference answers.

That comparison should measure correctness, unsupported-question handling, repeatability, traceability effort, latency, cost, authoring effort, and failure behavior. The objective is not to prove that one technique wins every category. It is to determine whether governed semantic execution provides sufficient control for the workloads that require it and whether Text-to-SQL remains useful within a clearly bounded exploratory role.

## Conclusion

Text-to-SQL is a valuable discovery tool, not the enemy of governed analytics. The unsustainable pattern is allowing generated queries to become the unreviewed source of recurring business truth. The proposed architecture retains AI-assisted exploration while placing approved definitions, deterministic planning, entitlements, controls, and evidence between natural-language interpretation and governed execution.
